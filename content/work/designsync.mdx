<Section number="01" eyebrow="The problem" title="Collaboration was *scattered.*" visual={<ScatterToHub hub="DesignSync" pills={["Chat threads","Shared drives","Email feedback","Design files","Tutorials","Task boards"]} />}>

Students, developers and design teams were spreading their work across too many places. Project collaboration lived in one tool, design submissions in another, feedback in chats and email, and learning resources somewhere else again.

The goal was one platform where a team could run a design project end to end, and learn system design along the way.

</Section>

<Section number="02" eyebrow="What I built" title="Three modules, *one platform.*">

<ModuleCard name="Studios" icon="board">
Project collaboration and design workflows: where teams plan work, submit designs and review them together.

- A project board with Active and Completed views, each card showing its status, client and due date
- New projects created and assigned to a client from the board
- Design submissions and client feedback, with reviews tracked per project
- Real-time collaboration and notifications, so updates appear without a refresh
</ModuleCard>

<ModuleCard name="Academy" icon="cap">
Structured system-design learning with real-world examples, so people learn how actual applications are designed, not just the theory.

- Assignments created by admins, with a status for each one (Pending, then Submitted)
- Students submit their work; admins open it and review it
- Lessons on architecture, scalability, databases, APIs, caching and real-time communication
- Worked examples, like how a ride-booking app handles requests, driver matching, live location and scale
</ModuleCard>

<ModuleCard name="Admin console" icon="shield">
The control room for the whole workspace: who can sign in, what they can do, and what is happening right now.

- A dashboard with total projects, active clients, pending approvals and active projects, plus a recent-activity feed
- User management: create login IDs that are approved at once, or approve and reject self-registered accounts
- Four roles (Admin, Designer, Enterprise Client, Academy Student), each seeing only its own part of the app
- Search, edit, delete and profile photos for every user, with light and dark themes across the app
</ModuleCard>

</Section>

<Section number="03" eyebrow="Architecture" title="REST for data, *sockets for now.*">

A React frontend talks to an Express API over REST for everything stored, and keeps a Socket.IO connection open for anything that has to appear instantly. Every request passes JWT authentication and a role check before it touches MongoDB.

<EngineeringDecisions title="Engineering decisions that *mattered.*">

<Decision n="i." title="Modular on both sides">
Reusable React + Tailwind components on the front and separate Express services on the back, so Studios and Academy share one foundation.
</Decision>

<EngineeringCard
  challenge="Keeping real-time events and REST data consistent"
  difficulty="When a client submits feedback over REST and a socket event fires immediately after, there's a race: the receiver might render stale data if the socket arrives before the database write completes."
  approach="REST writes happen first and fully commit to MongoDB. Only after the response is built from the saved document does the server emit the socket event — and it emits the populated document, not a bare notification."
  reasoning="Broadcasting the full document means the client can update its local state directly without a follow-up fetch, eliminating the race condition entirely."
  outcome="Collaborators see feedback appear in real time with zero inconsistency. The pattern also made debugging straightforward: every socket payload is inspectable and matches what the REST endpoint returns."
/>

<EngineeringCard
  challenge="Role-based access that cannot be bypassed from the frontend"
  difficulty="A role system that only hides buttons in the UI provides no real security. A determined user can call the API directly and bypass the restriction entirely."
  approach="Every protected route runs two middleware functions: one that verifies the JWT and attaches the user, and one that checks the user's role against an allowlist for that route."
  reasoning="Enforcing access on the server means the frontend is irrelevant to security. The UI still hides buttons for a clean experience, but the API enforces the boundary regardless of how the request arrives."
  outcome="Four roles — Admin, Designer, Enterprise Client, Academy Student — each with a strict, server-enforced boundary. Penetration testing confirmed no cross-role access was possible."
/>

<EngineeringCard
  challenge="Approving self-registered accounts without blocking the flow"
  difficulty="Users who register themselves need to be held in a pending state until an admin approves them, but the approval flow had to be seamless and not break the existing auth system."
  approach="A `status` field on the user document gates the sign-in check: JWT issuance only succeeds if `status === 'approved'`. Admins see a pending queue in the console and approve or reject with a single action."
  reasoning="Keeping the approval gate inside the auth flow means no separate approval service is needed, and the check is impossible to skip — it runs before the token is ever issued."
  outcome="Zero unauthorised logins. The admin queue became a core part of the platform's trust model and was delivered in the same sprint as the rest of the auth system."
/>

</EngineeringDecisions>

<HardestPart n="04" quote="Keeping the frontend and backend *in sync* while everything happened in real time.">

I traced the data flow end to end, from a click in React, through the API, to the Socket.IO event and back into the interface, and checked three things at every hop:

1. Each event is handled correctly
2. Updates reach only the intended users
3. The interface always shows the latest state

</HardestPart>

<Learnings n="05">
- **Asynchronous communication:** how requests, responses and events interleave, and where they can race.
- **Event-driven architecture:** designing around things that happen, not just data that's stored.
- **Full-stack debugging:** following one bug from the UI to the database and back.
</Learnings>
