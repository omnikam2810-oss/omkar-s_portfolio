<Section number="01" eyebrow="The problem" title="New codebase, *no map.*" visual={<ScatterToHub hub="RepoLens AI" pills={["Hundreds of files","Hidden dependencies","Unknown entry points","Missing docs","Mixed languages","Tribal knowledge"]} />}>

When developers join an existing project, they spend a lot of time just getting oriented: opening files one by one, tracing dependencies, and working out how the pieces fit together.

RepoLens AI is for developers, students and engineering teams facing an unfamiliar or complex codebase. It brings repository analysis, architecture visualisation, AI-assisted code understanding and documentation generation into one place, so people become productive faster.

</Section>

<Section number="03" eyebrow="How it works" title="From a URL to a *structured report.*">

The whole experience is three steps, and the report can be exported and shared.

1. **Paste a public repository.** RepoLens validates the GitHub URL and prepares the analysis.
2. **Build a repository snapshot.** The backend fetches the metadata, the directory structure and the high-signal files.
3. **Generate structured insight.** Gemini returns a typed report, which the dashboard renders as scores, sections and the repository map.

</Section>

<Section number="04" eyebrow="Architecture" title="A pipeline, *one stage at a time.*">

Reading files one at a time can't reveal a whole architecture, so RepoLens turns a repository into a structured representation first. Each stage has one job: import the repo, analyse its file structure, parse the source with Tree-sitter, draw the architecture with Graphviz, and only then hand that structure to the LLM to explain.

<Section number="05" eyebrow="Key decisions" title="Three choices that *shaped it.*">

<Decision n="i." title="Deterministic tools for facts">
Tree-sitter extracts the real structure of the code, and Graphviz draws it. The diagrams come from parsing, not from a model's guess.
</Decision>

<Decision n="ii." title="The LLM explains, it doesn't discover">
The model receives a snapshot that has already been extracted and returns a typed report (scores, sections, suggestions), so the dashboard renders fields it can rely on instead of parsing free text.
</Decision>

<Decision n="iii." title="OpenAI-compatible by design">
Building against an OpenAI-compatible API means the provider can be swapped by configuration, with local inference through Ollama as a future option.
</Decision>

</Section>

<HardestPart quote="Turning a whole repository into *one structured picture* an interface and an LLM could both use.">

Many files and interconnected components meant reading files one by one wasn't enough. I split the work into a pipeline where every stage has a single, clear responsibility:

1. Import the repository and analyse its file structure
2. Parse the source code with Tree-sitter to recover components and relationships
3. Visualise the architecture with Graphviz, then pass the structure to the LLM for explanations

</HardestPart>

<Learnings>
- **Structure beats skimming:** understanding a large codebase needs structured analysis, not reading files one by one.
- **Tools and LLMs do different jobs:** Tree-sitter and Graphviz extract and show structure; the LLM explains it in natural language.
- **Modularity pays off:** keeping import, architecture recovery, AI chat, documentation and code quality separate makes the app easier to maintain and extend.
</Learnings>
