<Section number="01" eyebrow="The problem" title="Consistency needs *a good log.*" visual={<ScatterToHub hub="FitTrack" pills={["Notes app","Spreadsheets","Paywalled apps","Memory","Photos","Chat logs"]} />}>

FitTrack is for people who want to record their workouts and keep a consistent routine. Staying consistent starts with tracking, and tracking has to be quick enough to do between sets on a phone.

The goal is a mobile-friendly experience for fitness tracking, backed by a real API and database so that data stays reliable and in sync.

</Section>

<Section number="02" eyebrow="What I built" title="A gym log, *in your pocket.*">

<ModuleCard name="Mobile app" icon="dumbbell">
Built with React Native and Expo, so most of the code is shared across platforms.

- Log a workout as exercises and sets, with weight, reps and a completed tick for each set
- Totals for volume, sets and muscle groups are worked out for you when a workout is saved
- A numeric keypad made for entering sets quickly
- An exercise library, training programs and body measurements
- A community feed, plus an onboarding flow for new users
</ModuleCard>

<ModuleCard name="Backend & media" icon="image">
A Node/Express API with MongoDB for data, and Cloudinary for media storage.

- REST API for app data
- MongoDB for users and workouts
- Cloudinary for images
</ModuleCard>

</Section>

<Section number="03" eyebrow="Architecture" title="Mobile front, *containerised back.*">

The Expo app talks to an Express API over REST. The API and MongoDB run in Docker, and media goes to Cloudinary so the API stays light.

<EngineeringCard
  challenge="Docker networking: localhost isn't where you think"
  difficulty="Inside a container, `localhost` resolves to that container itself — not to the MongoDB container running alongside it. The API silently failed to connect to the database on first boot."
  approach="Both the API and MongoDB were placed on the same named Docker network. The connection string was updated to use the service name as the hostname (`mongodb://mongodb:27017/fittrack`) and moved to an environment variable."
  reasoning="Docker's internal DNS resolves service names on a shared network. Using a service name instead of `localhost` is portable: the same connection string works in development, CI, and production without modification."
  outcome="The API connects to MongoDB reliably in all environments. The environment-variable approach also means no connection string is ever committed to source control."
/>

<EngineeringCard
  challenge="Sharing code across Android and iOS without diverging"
  difficulty="Native mobile development typically means two separate codebases. Even with cross-platform tools, platform-specific UI quirks can force divergence that grows over time."
  approach="React Native with Expo was chosen as the foundation. Platform-specific code is isolated to a small number of files using `.ios.tsx` / `.android.tsx` extensions; shared business logic and UI live in a single tree."
  reasoning="Expo abstracts most platform differences and provides a managed build workflow. For a project where feature parity between platforms mattered more than deep native customisation, the tradeoff was clearly worth it."
  outcome="A single codebase delivers the same experience on Android and iOS. The numeric keypad — the most interaction-critical component — works identically on both platforms with no platform-specific code."
/>

<EngineeringCard
  challenge="Keeping media off the server without losing references"
  difficulty="Storing images on the API server bloats its disk, complicates backups, and doesn't scale. But handing uploads directly to Cloudinary from the client exposes API credentials."
  approach="The API accepts the image file, streams it to Cloudinary using the Node SDK, receives the hosted URL in response, and stores only that URL in MongoDB. The client never talks to Cloudinary directly."
  reasoning="The server acts as a trusted intermediary, keeping credentials secret while remaining responsible for all external service calls. MongoDB stays lean — it stores strings, not blobs."
  outcome="The API binary stays small and stateless. Cloudinary handles delivery, transformation and CDN caching. The pattern is straightforward to replicate for any future file type."
/>

</EngineeringDecisions>
