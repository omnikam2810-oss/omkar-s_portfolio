<Section number="01" eyebrow="The problem" title="Something broke, *and the clues are everywhere.*" visual={<ScatterToHub hub="DevTrace" pills={["Metrics","Logs","Traces","Deploys","Alerts","Dashboards"]} />}>

When a service slows down, the evidence is split across tools: metrics in one place, logs in another, traces somewhere else, and nobody remembers which release shipped when. The engineer on call spends the first half hour just collecting it.

DevTrace is a self-hosted observability platform, in the same space as Datadog, New Relic and Sentry. You connect your applications to it, and it shows how they are behaving and why they break, in one console.

</Section>

<Section number="03" eyebrow="Architecture" title="Acknowledge fast, *process in the background.*">

An application sends its telemetry in batches. The ingest API checks the batch and puts it on a Redis queue, then replies `202` straight away. BullMQ workers pick it up and write it to PostgreSQL through Prisma, evaluate the alert rules, and push live updates to the console over Socket.IO.

<Section number="04" eyebrow="In practice" title="A checkout that *slows down.*">

A company runs `checkout-api` and `payments-api`. On Friday evening, customers report slow checkouts. This is how DevTrace takes the on-call engineer from the first alert to a fix.

1. **Detection.** The agent in `checkout-api` has been sending metrics every few seconds. An alert rule ("latency over 800 ms for 5 minutes") fires, and an incident opens on its own.
2. **Triage.** In the console, `checkout-api` shows as degraded. The service map draws its edge to `payments-api` in red, with a 6% error rate.
3. **Root cause.** In the trace waterfall, most of each slow request is a single span: a database call inside `payments-api`. Filtering the logs by that trace ID shows connection-pool timeout errors.
4. **Correlation.** The Deployments page shows `payments-api` v2.4.1 shipped 20 minutes before the alert, which points at the release.
5. **Resolution.** They roll back, health scores recover, and the incident is closed with a root cause and notes. The Gemini analysis can draft that summary from the evidence.
6. **Follow-up.** On Monday the weekly PDF report lists the incident and the service's health trend, so the team can review it.

</Section>

<EngineeringDecisions title="Engineering decisions that *mattered.*">

<Decision n="i." title="The AI suggests, the evidence decides">
Gemini drafts root-cause suggestions and incident summaries, but only from the incident's own evidence: the traces, logs and deployments already attached to it. An engineer reviews it before anything is closed.
</Decision>

<EngineeringCard
  challenge="Staying responsive when the platform receives its heaviest traffic during an outage"
  difficulty="An observability platform gets its peak load exactly when its customers are having an incident. If the ingest API is slow or down during that moment, the data needed for diagnosis is lost."
  approach="The ingest API validates the payload and immediately enqueues it to a Redis BullMQ queue, then responds `202 Accepted`. Workers running in separate processes pick up the job and do the slow work: writing to PostgreSQL, evaluating alert rules, and pushing live updates."
  reasoning="Decoupling ingest from processing means the API's response time is bounded by queue insertion speed, not by database write speed. Workers can slow down or fail without affecting the ingest path."
  outcome="In a load test, the platform sustained approximately 6,000 items per second with a p95 ingest latency of 113 ms — well within acceptable bounds for an observability workload."
/>

<EngineeringCard
  challenge="Querying time-series data at scale without bulk deletes"
  difficulty="Metrics and logs from busy services accumulate fast. Without a strategy, tables grow until queries slow to a crawl. Bulk deletes on large tables can lock rows and block reads."
  approach="PostgreSQL monthly partitions on the metrics and logs tables. Each month's data lives in its own child table. Retention jobs drop entire partitions — a metadata-only operation — rather than running `DELETE` statements."
  reasoning="Dropping a partition is orders of magnitude faster than bulk-deleting rows. Queries that filter by time can skip irrelevant partitions entirely, keeping p99 read latency stable as data accumulates."
  outcome="Partition pruning keeps queries fast as the dataset grows. Retention is a one-line operation: `DROP TABLE metrics_2026_09`. No locks, no slow scans."
/>

<EngineeringCard
  challenge="Correlating metrics, traces, logs and deployments in one incident view"
  difficulty="The root cause of an incident is rarely visible in a single signal. Seeing a latency spike in isolation doesn't tell you which service caused it, what the trace looks like, what the logs say, or whether a deployment happened around the same time."
  approach="Every telemetry type — metrics, logs, traces, heartbeats — shares a `projectId` and a `traceId` where applicable. The incident view is a join across all four, filtered by the incident's time window. Deployments are stored with timestamps and shown on the same timeline."
  reasoning="Sharing a common identifier across telemetry types makes correlation a query, not a manual investigation. The engineer sees all the evidence for an incident in one place because the data model was designed for it from the start."
  outcome="The worked example (a checkout slowdown caused by a bad release) can be investigated entirely within DevTrace: from the alert, to the service map, to the trace, to the log, to the deployment, in a single session."
/>

</EngineeringDecisions>

<Learnings n="07">
- **Queues decouple:** a fast acknowledgement and background workers keep a system responsive when load spikes.
- **Time-series data needs a plan early:** partitioning and retention are far easier to design in than to add once the tables are huge.
- **Observability is correlation:** a metric, a trace, a log line and a deploy time only explain a failure when they sit side by side.
</Learnings>
